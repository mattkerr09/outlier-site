V11 streaming engine benchmarks (and why V10 ships instead)

Outlier · last updated May 20, 2026

Quick answer

  • Three paged-MoE inference engines benchmarked on Mac Studio M1 Ultra 64 GB: V9, V10, V11.
  • V11 with hybrid LRU showed best smoke numbers (Plus 3.0 tok/s, 7.34 GB peak gen RAM in MLX-internal alloc tracker).
  • Multi-turn soak revealed V11's LRU pinned tens of GB of Metal-wired memory; OS-level RSS hit ~55 GB on Plus chat.
  • V10 streaming (no LRU) holds the same ~2.9 tok/s at 4× less RAM. V10 ships in default config from v1.11.71.

Three paged-MoE inference engines were benchmarked on a Mac Studio M1 Ultra 64 GB during May 2026: V9 (baseline), V10 (no-LRU streaming), V11 (hybrid LRU streaming). V11 looked like the clear winner on smoke benchmarks; soak testing revealed a memory-pinning problem that doesn't show up in single-prompt smokes. V10 is what ships. This page is the data that drove the call.

Why three engines

Running a 397-billion-parameter Mixture-of-Experts model on a 64 GB Mac requires paging the experts off SSD per token. The naive approach (read all experts every token) is bound by SSD bandwidth. The clever approaches cache hot experts in RAM and read cold experts as needed. The question is how aggressive should the cache be — bigger cache means faster steady state but more RAM, smaller cache means lower memory ceiling but more SSD reads.

  • V9 baseline — full set of routed experts loaded into RAM, no paging. Hits a hardware ceiling: 96 GB minimum for Plus 397B. Doesn't run on a 64 GB Mac.
  • V10 streaming — read top-K experts off SSD per token, no in-RAM cache. Pure paging. Memory floor: ~7 GB engine + per-token slice.
  • V11 hybrid LRU — small cache of recently-used experts in RAM (size N=4 for Plus, N=2 for Vision); cache misses page from SSD. Hopes to amortize SSD reads across consecutive tokens that activate similar experts.

Methodology

  • Hardware: Mac Studio M1 Ultra, 64 GB unified memory, internal SSD ~7.4 GB/s
  • OS: macOS 25.3 (Darwin 25.3.0), iogpu.wired_limit_mb=57344
  • Models: Plus 397B-A17B at MLX 4-bit (mlx-community/Qwen3.5-397B-A17B-4bit); Vision 35B-A3B at MLX 4-bit (Outlier-Ai/Outlier-Vision-35B-A3B-MLX-4bit)
  • Protocol: separate-process repetition, n=5 reps, 5 prompts × 80 tokens each, mean and stderr documented
  • Cold-start control: each rep boots a fresh backend; first 10 tokens excluded from rate calculation
  • Coherence rubric: 5/5 means each prompt's response was scored coherent (correct on its task, no repetition collapse) by manual inspection

V11 looked like the right call on these numbers. Plus 1.80× V9 with a similar memory footprint to V10. Vision a 20× memory reduction (16 GB MacBook Air capable). Promoted to opt-in in v1.8.53.

Multi-turn soak — the surprise

The opt-in shipped on 2026-05-08. Track 2 soak ran 8 hours, 9 cycles, 135 multi-turn conversations. Verdict was CLEAN on correctness — 135/135 turns coherent, 0 crashes. But the memory column told a different story than the smokes:

WorkloadEngineSmoke peak (MLX-internal)Multi-turn-50 peak (MLX-internal)
Plus 397BV11 K=4 N=4 LRU7.34 GB14.34 GB
Vision 35B-A3BV11 K=2 N=2 LRU1.60 GB3.16 GB

14.34 GB on a 50-turn Plus session is higher than V9's 13.75 GB. The LRU's memory advantage inverts on long workloads — the cache grows as conversation context grows.

The bigger gap revealed two weeks later. When we instrumented OS-level RSS (Activity Monitor reading, not mx.get_peak_memory() which only sees MLX-internal allocator), Plus on V11 during real chat hit roughly 55 GB OS RSS on a 64 GB Mac. The LRU was pinning Metal-wired memory that the OS counted but the MLX tracker didn't. Engine picker copy that said "1.60 GB" or "7 GB" had been telling MLX-internal numbers, not what the user's OS saw.

V10 versus V11 — the head-to-head that mattered

On 2026-05-19, we re-ran Plus 397B on V10 (no LRU, pure streaming) and V11 (hybrid LRU) using the same prompts and recording both MLX-internal alloc and OS-level RSS:

EnginePlus tok/sMLX-internal peakOS-level RSS during chat
V10 streaming~2.9~7 GB~13 GB
V11 hybrid LRU~2.9–3.0~7.3 GB~55 GB

V11 holds no perceptible tok/s advantage in steady-state chat while quadrupling OS-level RAM. v1.11.71 removes V11 from the shipping config. Users stored on v11_streaming auto-migrate to v10_streaming on next backend start. Plus on V10 streaming is the current recommendation: under 14 GB peak on a 64 GB Mac, no swap pressure even with other apps running.

The honest finding behind this page

Smoke benchmarks can mislead in two ways at once:

  • (1) Short workload masks long-workload behavior. An LRU cache that's empty at smoke time has nowhere to grow; on a 50-turn chat it does.
  • (2) The wrong instrument masks the actual problem. MLX's internal allocator doesn't see Metal-wired memory. Activity Monitor does. The picker copy that said "7 GB" was reading the wrong column.

The corrective action shipped as two changes: (a) the engine picker now shows tier-aware honest numbers (see /learn/what-is-paged-moe-inference/), and (b) the picker pulls OS-level peak, not MLX-internal peak.

Reproduce this yourself

The V10/V11 engine code is in the public Outlier app bundle. To re-run the K-sweep on your own Mac:

  1. Install Outlier v1.10.x (the last version with V11 opt-in available) from the release archive at github.com/Outlier-host/outlier-app-releases/releases
  2. Enable V11 in Settings > Engine Mode > V11 Streaming (beta)
  3. Reproduce the 5×80-token sweep with a fresh process per rep; Activity Monitor open
  4. Re-run on default (V9 for Plus or V10 streaming on current builds) for the comparison column

Note: v1.11.71+ removes the V11 toggle entirely. The benchmark is reproducible only on older bundles.

Where free tools sit on this dimension

Neither Ollama nor LM Studio nor Jan currently runs Qwen3.5-397B on a 64 GB Mac. The model is 209 GB on disk; none of these tools page MoE experts off SSD per token. See Local AI on Mac — Outlier vs Ollama vs LM Studio vs Jan.
