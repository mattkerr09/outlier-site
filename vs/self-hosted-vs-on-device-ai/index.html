Self-hosting an LLM vs running it on-device

Matt Kerr · Outlier · published 2026-07-23 Updated 2026-07-23
Quick answer

Self-hosting an LLM means running open-weight model files yourself on a GPU server you rent or own — usually vLLM or llama.cpp behind an OpenAI-compatible HTTP API. On-device means the same class of open weights runs inside an app on the user's own machine, with no server in the path. Self-hosting wins on model size and concurrency; on-device wins on recurring cost, offline operation, and the fact that no prompt crosses a network.

Both approaches run the same open weights on hardware you control. The difference is whose hardware, and that choice cascades: model size ceiling, concurrency, monthly cost, ops load. Disclosure up front — I build Outlier, a Mac app that takes the on-device route, so I'm an interested party here.

What self-hosting actually means

You put open weights on a disk attached to a GPU and start an inference server that loads them into VRAM and speaks HTTP. Usually one of three. vLLM (Apache-2.0) targets NVIDIA, AMD and Intel GPUs plus x86/ARM/PowerPC CPUs. llama.cpp (MIT) ships llama-server, "a lightweight, OpenAI API compatible, HTTP server for serving LLMs," covering Metal, CUDA, Vulkan and SYCL with 1.5-bit through 8-bit quantization. Ollama (MIT) wraps the same idea in a REST API on http://localhost:11434.

What makes vLLM the default for serious serving is PagedAttention: it partitions the KV cache into blocks the way an OS pages memory, which the project says cuts cache waste from 60–80% to under 4% and lets you batch far more sequences onto one card. Their launch post claimed up to 24× the throughput of naive Hugging Face serving — June 2023, against 2023 baselines, so read it as a historical marker, not a current head-to-head.

What on-device actually means

Same weights, different destination: downloaded to the user's machine, loaded into that machine's memory, inference in-process. On Apple Silicon the usual substrate is MLX (MIT), built around unified memory — "arrays in MLX live in shared memory. Operations on MLX arrays can be performed on any of the supported device types without transferring data." That erases the host-to-VRAM copy, and the model's budget becomes your whole RAM rather than a separate 24 GB or 80 GB pool.

The ceiling is whatever the machine shipped with, and you can't add more later. Outlier is one example: tiers from Nano (4B, 2.37 GB download, 6 GB RAM, 71.7 tok/s on an M1 Ultra) up to Plus (397B-a17b, a 209 GB download needing 64 GB of RAM, running 2.1 tok/s by paging MoE experts off the SSD at ~11 GB peak RSS). That top tier is the on-device answer to "the model doesn't fit," and the price is speed. Every on-device stack hits the same wall.

The two stacks also don't share hardware. vLLM's install matrix targets NVIDIA CUDA, AMD ROCm, Intel XPU and CPU; Apple Silicon appears only "via vLLM-Metal," a separate project outside the main repo, plus CPU-only support. Self-hosting means NVIDIA and CUDA; on-device on a Mac means Metal and MLX. llama.cpp is the one runtime spanning both.

Where self-hosting genuinely wins

These are real, and I'm not going to soften them.

  • Model size has no ceiling. --tensor-parallel-size splits one model across GPUs, so a rack serves DeepSeek-V3 — 671B total parameters, 37B activated per token — or gpt-oss-120b, which needs an 80 GB GPU. No laptop holds those.
  • Concurrency is the real differentiator. Continuous batching plus PagedAttention means one GPU serves a team; an on-device app serves exactly one person. With 40 engineers, the math isn't close.
  • Bandwidth. 3.35 TB/s on an H100 SXM is what makes long-context prefill and large-batch decode quick — the dimension where datacenter silicon most clearly beats a desktop.
  • One endpoint, many clients. vLLM and llama-server both speak the OpenAI API, so a single deployment backs laptops, phones, CI jobs and internal tools with one upgrade path.
  • Operability. Versioned config, container deploys, central logs, per-key auth. You can answer "what did we ask the model last Tuesday" across an org — impossible across desktop installs.
  • It offloads the work. No battery drain, no thermal throttling, no multi-gigabyte footprint fighting the user's real apps, and jobs survive a closed laptop.
  • Data control can equal on-device when the hardware is literally yours. On your own metal or VPC, prompts never reach a model vendor and retention is your policy.

Where on-device genuinely wins

The bill never arrives. RunPod's H100 PCIe is $2.89/hr — roughly $2,110/month at 730 hours if you leave it up — and even a 4090 pod is about $504/month. Lambda's single H100 SXM is $4.29/GPU/hr; Hugging Face Inference Endpoints run $0.80/hr for an L4 to $4.50/hr for an H100. Fair prices for real hardware; they just don't stop. You pay for idle too: pods bill from worker start to full stop, and even scale-to-zero Flex workers keep a billed idle timeout and reintroduce cold starts, trading money for first-token latency.

Nothing crosses a network. Unless the server is in your building, every request enters a datacenter with physical custody of the box and the RAM the model runs in. AWS's data-privacy FAQ says "we do not access or use your content for any purpose without your agreement," but that page doesn't explicitly address AI/ML training use — you'd confirm that in the service terms, and the answer differs per provider. On-device sidesteps the question rather than answering it.

Security is structural, not configured. Ollama binds 127.0.0.1:11434, and its FAQ's answer for network access is Nginx, ngrok or Cloudflare Tunnel — auth is what the operator adds. vLLM's --api-key is a header check, a floor rather than a security model. A misconfigured bind is an unauthenticated inference endpoint on the internet; an app with no listening socket has no such failure mode.

And there's no infrastructure. vLLM's Kubernetes guide wants a GPU-capable cluster, a PVC for model storage, a Secret holding a Hugging Face token, and a shared-memory volume for tensor parallelism — before TLS, rate limiting or on-call.

One thing neither side escapes: licenses

Open weights aren't automatically open source. Llama 3.3 requires a separate license from Meta above 700 million monthly active users and mandates "Built with Llama" attribution. DeepSeek-V3's code is MIT, but the weights sit under a separate Model License. Qwen3.6-27B is plain Apache-2.0, as is gpt-oss-20b. Even Open WebUI adds a branding clause you only escape under 50 end users per 30 days.

Who should pick which

Self-host if you need a model no consumer machine can hold, you're serving more than one person, you need central audit logs and key rotation, or you run long-context and batch work where 3+ TB/s of bandwidth is the point. Also self-host when compliance requires inference on hardware your organization owns — something on-device can't satisfy at fleet scale.

Go on-device if the workload is one person at a time, the recurring bill is the problem, the machine has to work without a connection, or the data is the kind you'd rather not transit anyone's network. Outlier is one implementation of that shape — Apple Silicon only, M1 or later, macOS 12+, no account, no caps, nothing uploaded, free at the Nano and Lite tiers. It has no web search, no image generation, no mobile app, no voice mode and no Windows or Linux build, because those are the costs of the architecture. LM Studio, Jan, and a locally compiled llama.cpp are the same category with different trade-offs.

Plenty of teams run both: a shared server for the big model and the batch jobs, an on-device app for the sensitive and offline work. The right answer changes per task.
